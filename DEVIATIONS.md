# DEVIATIONS.md — Judgment-Call Log

**Append-only.** Never edit or delete a past entry. When a decision is
reversed, add a **new** entry that references the old one.

Log an entry whenever a judgment call is made that is **not** explicitly
resolved by [PRD.md](PRD.md) / [ARCHITECTURE.md](ARCHITECTURE.md): an ambiguous
requirement interpreted one way, an edge case handled without instruction, or a
default chosen where the spec was silent. Log at the moment the call is made,
not retroactively. When in doubt, log it.

**Entry format**

```
### <n>. <short title>
- **Date / phase:** YYYY-MM-DD / Phase N
- **Requirement ID(s):** PRD-### / ARCH-### / SCOPE-#.# / — (none)
- **Ambiguous or undecided:** what the spec left open or unclear
- **Decision & rationale:** what was chosen and why
- **Reversible?:** yes / partially / no — and what reversal would cost
```

## Phase 0

### 1. Vector store: Qdrant chosen over ChromaDB
- **Date / phase:** 2026-08-27 / Phase 0
- **Requirement ID(s):** ARCH-002, PRD-104
- **Ambiguous or undecided:** The brief said "ChromaDB or Qdrant — pick one and justify it."
- **Decision & rationale:** Qdrant. Native dense+sparse hybrid with server-side RRF fusion, fast payload filtering (needed to enforce access scope *inside* the query, which is security-relevant here), and stronger production/operational features. Chroma is simpler but weaker on native sparse/hybrid and large-scale filtering. Full justification in ARCHITECTURE.md §3.
- **Reversible?:** partially — a `VectorStore` adapter interface is planned; swapping to Chroma would mean losing native sparse/hybrid and re-implementing fusion, plus a re-index. Cost: moderate.

### 2. Inter-rater reliability metric: Krippendorff's alpha (ordinal)
- **Date / phase:** 2026-08-27 / Phase 0
- **Requirement ID(s):** ARCH-021, PRD-044
- **Ambiguous or undecided:** Brief said "pick one and justify it (e.g. Krippendorff's alpha or an ICC variant)."
- **Decision & rationale:** Krippendorff's alpha with the ordinal difference function, per rubric domain. Handles a variable, non-fixed rater panel (raters self-select items from the queue), ordinal 5-point data, and missing values — none of which Cohen's/Fleiss' kappa or interval ICC handle cleanly. Gwet's AC2 and ICC(2,k) are computed as *secondary* descriptive statistics. Full justification in ARCHITECTURE.md §14.4.
- **Reversible?:** yes — all raw scores are stored structurally; any metric can be recomputed retrospectively.

### 3. Relational store: PostgreSQL as single system of record
- **Date / phase:** 2026-08-27 / Phase 0
- **Requirement ID(s):** ARCH-008
- **Ambiguous or undecided:** The brief specified FastAPI, Redis/Celery, a vector store, and LangGraph, but did not name an RDBMS. A relational store is needed for HITL/rubric/audit/memory transactional integrity.
- **Decision & rationale:** PostgreSQL, one database with multiple schemas (`corpus`, `records`, `memory`, `hitl`, `eval`, `audit`, `iam`). Reasons: transactional integrity across the rubric/HITL/audit workflow, JSONB for semi-structured payloads, row-level security for PHI scoping, `pgcrypto` for field encryption, and a supported LangGraph Postgres checkpointer.
- **Reversible?:** partially — schema migrations would be needed to move to another RDBMS; the ORM layer abstracts most of it. Cost: moderate.

### 4. Auth: seeded dev-JWT for MVP instead of a full OIDC IdP
- **Date / phase:** 2026-08-27 / Phase 0
- **Requirement ID(s):** ARCH-011, PRD-086
- **Ambiguous or undecided:** PRD-086 requires RBAC with clinician/reviewer/admin roles but does not mandate a specific IdP; "production-grade patterns, minimal feature surface" (PRD-C5) pulls against standing up Keycloak now.
- **Decision & rationale:** An `AuthProvider` interface with a seeded signed-JWT issuer for dev (roles included) plus an OIDC adapter **stub**. Keycloak is available only in the `full` docker-compose profile. Keeps the seam without the MVP operational cost.
- **Reversible?:** yes — the OIDC adapter is a drop-in; no data migration.

### 5. Encryption: envelope-encrypt free-text/blob PHI fields; inter-service TLS partial
- **Date / phase:** 2026-08-27 / Phase 0
- **Requirement ID(s):** ARCH-031, ARCH-032, PRD-082, PRD-083
- **Ambiguous or undecided:** "Encryption at rest and in transit" is mandated as core, but the spec does not define the granularity (per-column field encryption vs blob) or whether mTLS between every internal service is required for a single-host self-hosted MVP.
- **Decision & rationale:** At rest — host volume encryption (documented deployment prerequisite) **plus** application-level envelope encryption for the free-text / blob PHI fields enumerated in ARCHITECTURE.md §17.2; structured record fields live inside the encrypted `payload_enc` blob and are served via the record accessor rather than as individually-encrypted columns. In transit — TLS at the reverse proxy, a private compose network with authenticated Postgres/Redis/Qdrant, and inter-service TLS where the image supports it trivially; full mTLS between every service is documented as a production hardening item, not done in the MVP. The `CryptoProvider` abstraction stays so per-column encryption can be added later.
- **Reversible?:** yes — additive hardening; no data model change to add more encrypted columns or mTLS later.

### 6. Audit tamper-evidence: prev-hash chain only; no external anchoring in MVP
- **Date / phase:** 2026-08-27 / Phase 0
- **Requirement ID(s):** ARCH-035, PRD-085
- **Ambiguous or undecided:** "Immutable audit logging" is mandated; the spec does not specify the mechanism or whether external timestamping/anchoring is required.
- **Decision & rationale:** Append-only enforced by DB grants (`INSERT, SELECT` only for the app role; no `UPDATE`/`DELETE`), plus a `prev_hash`/`row_hash` chain and a chain-verifier job. External timestamping/anchoring to an independent service is deferred as over-engineered for the MVP (self-critique §21c).
- **Reversible?:** yes — anchoring can be layered on later without changing existing rows.

### 7. Stage-classifier and missing-info kept as distinct agents (not merged into synthesis)
- **Date / phase:** 2026-08-27 / Phase 0
- **Requirement ID(s):** ARCH-016, SCOPE-2.1, SCOPE-2.2
- **Ambiguous or undecided:** These two functions could be implemented as prompt modes / tools on the guideline-synthesis agent, which would be fewer moving parts (PRD-C5 favours minimal surface).
- **Decision & rationale:** Kept as separate LangGraph agents with their own tool allow-lists and audit outcomes. Rationale: the SCOPE boundary (in-scope classification/clarification vs. excluded next-step recommendation) must be legible and independently testable; a merged agent makes it easy to accidentally let patient data + guidelines flow into a recommendation. The extra structure is a deliberate safety cost.
- **Reversible?:** yes — could be collapsed later, but the boundary tests would need re-homing.

### 8. Patient-record vectorization OFF by default
- **Date / phase:** 2026-08-27 / Phase 0
- **Requirement ID(s):** ARCH-023, PRD-NFR-5, PRD-080
- **Ambiguous or undecided:** The brief mentions patient records "via flat file or API" and hybrid retrieval, but does not say whether patient-record content is embedded/retrieved like documents.
- **Decision & rationale:** SCOPE-2 flows read structured record fields directly and match them against retrieved *guideline* criteria; patient records are **not** embedded. A `PATIENT_RECORD_VECTORS_ENABLED=false` flag gates any future record vectorization, which if enabled would use a separate Qdrant collection with mandatory `patient_id` payload filtering. Minimises PHI surface.
- **Reversible?:** yes — flag + separate collection; additive.

### 9. "Hard cases" defined as missing_info_expected + no_guideline_expected combined
- **Date / phase:** 2026-08-27 / Phase 0
- **Requirement ID(s):** ARCH-022, PRD-065
- **Ambiguous or undecided:** The brief says hard/adversarial cases "must not exceed 50%" and to use a 60/20/20 split, but does not define precisely which buckets count as "hard".
- **Decision & rationale:** "Hard/adversarial" = `missing_info_expected` + `no_guideline_expected` combined. Under the mandated 60/20/20 split that is 40%, satisfying the ≤50% cap with margin. The set planner enforces both the split and the cap.
- **Reversible?:** yes — composition is a config value (`QGEN_COMPOSITION`) and regeneration is cheap.

### 10. Constraint #6 (no hardcoded model) extended to embedding and reranker models
- **Date / phase:** 2026-08-27 / Phase 0
- **Requirement ID(s):** PRD-101, PRD-103, ARCH-004, ARCH-012
- **Ambiguous or undecided:** Constraint #6 names "the LLM". It is silent on the embedding model and the reranker, which are also model identifiers that would otherwise be hardcoded.
- **Decision & rationale:** Applied the same rule: `EMBEDDING_MODEL_ID` and `RERANKER_MODEL_ID` come from config with placeholder defaults (`BAAI/bge-large-en-v1.5`, `BAAI/bge-reranker-v2-m3`), both explicitly marked **UNVERIFIED — flagged** pending operator confirmation. The code contains no model name it depends on.
- **Reversible?:** yes — config only.

### 11. "Three HITL modes" interpreted as: rank axis + accept axis (full/partial/reject)
- **Date / phase:** 2026-08-27 / Phase 0
- **Requirement ID(s):** ARCH-018, ARCH-019, PRD-031, PRD-032
- **Ambiguous or undecided:** The brief says "the three HITL interaction modes required: multi-dimensional output ranking, full accept, partial accept, and reject" — which lists four things but calls them three modes.
- **Decision & rationale:** Modelled as **two independent axes** captured in one review sitting (`rating_round`): (1) **rank mode** = the 11-domain rubric; (2) the **accept axis** with three actions — full accept / partial accept / reject. Rank and accept are independent and both recorded; "three modes" is read as the three accept-axis actions, with ranking as the separate structured-evaluation mode. Both axes' effects on state are defined in ARCHITECTURE.md §13.
- **Reversible?:** yes — data model stores the axes separately; presentation can be re-grouped.

### 12. Conversation hot-state in Redis; durable memory + LangGraph checkpoints in Postgres
- **Date / phase:** 2026-08-27 / Phase 0
- **Requirement ID(s):** ARCH-016, ARCH-017, PRD-022, PRD-023
- **Ambiguous or undecided:** PRD-022 requires persistent memory and names categories but not the storage split; "where it lives" was left to design.
- **Decision & rationale:** Durable conversation/message/patient_context in Postgres (system of record); Redis holds only the active window, streaming partials, and counters with a TTL and is authoritative only until persisted; LangGraph uses the Postgres checkpointer so long runs survive restarts and are inspectable.
- **Reversible?:** yes.

### 13. Citation "chunk offset" realised as chunk_id + char span + section path + page
- **Date / phase:** 2026-08-27 / Phase 0
- **Requirement ID(s):** ARCH-014, PRD-011
- **Ambiguous or undecided:** Constraint #4 requires "document ID + page/section + chunk offset, minimum" without defining "chunk offset".
- **Decision & rationale:** "Chunk offset" is implemented as the `chunk_id` (the atomic retrieved unit) plus `char_start`/`char_end` offsets within the normalized document text, alongside `section_number`/`section_path` and `page_start`/`page_end`, and a verbatim `quote` with its own offsets for highlight + grounding re-verification.
- **Reversible?:** yes — additive fields; the minimum set is a subset.

### 14. No reviewer available for an escalation → hold + safe templated message, no auto-release
- **Date / phase:** 2026-08-27 / Phase 0
- **Requirement ID(s):** ARCH-018 (`ESCALATION_SLA_MINUTES`), PRD-Q2
- **Ambiguous or undecided:** The brief defines escalation triggers but not the behaviour when no human reviewer is available within a reasonable time (e.g. after hours).
- **Decision & rationale:** The escalation stays `open`; the clinician sees a held state with a safe templated message ("this response needs clinician review before it can be shown; no independent recommendation is available"); the candidate answer is **not** auto-released. Fail-safe over fail-open, consistent with PRD-NFR-2.
- **Reversible?:** yes — the SLA and the fallback behaviour are config/policy.

### 15. Cohort / multi-patient questions out of scope; one patient per conversation
- **Date / phase:** 2026-08-27 / Phase 0
- **Requirement ID(s):** PRD-NG-011, ARCH-016
- **Ambiguous or undecided:** The brief centres on patient-level records and hypotheticals but does not explicitly address cohort/population queries.
- **Decision & rationale:** A conversation is bound to at most one `patient_id`; cohort/population/cross-patient analytic queries are rejected by the orchestrator. Reduces PHI surface and keeps the grounding/scope model simple for the MVP.
- **Reversible?:** partially — enabling cohorts would need memory-model and access-control changes.

### 16. Ingestion refuses batches that fail a "looks like real data" heuristic
- **Date / phase:** 2026-08-27 / Phase 0
- **Requirement ID(s):** PRD-081, PRD-C1
- **Ambiguous or undecided:** "No real PHI, ever" is a policy; the brief does not require a technical control to detect accidental real-data ingestion.
- **Decision & rationale:** Added a warning-level heuristic (e.g. entropy/plausibility checks on names/identifiers) that hard-errors an ingestion batch it suspects is real. This is defence-in-depth, not a guarantee; the policy prohibition remains the primary control.
- **Reversible?:** yes — the check is a toggle and is heuristic only.

### 17. Straight-lining / low-variance rater rule deferred (scores still count for now)
- **Date / phase:** 2026-08-27 / Phase 0
- **Requirement ID(s):** ARCH-020, PRD-042
- **Ambiguous or undecided:** The multi-rater workflow does not say how to handle a rater who gives near-identical scores across all domains (possible fatigue/inattention), which affects IRR.
- **Decision & rationale:** For Phase 0/1, such raters are **flagged for QA** but their scores **still count** toward the 3-rater minimum and IRR. A concrete exclusion/weighting rule is deferred to when real rating data exists; this entry will be superseded by a new one when the rule is set.
- **Reversible?:** yes — raw scores are retained; any rule can be applied retrospectively.

### 18. Unit / locale normalization not attempted in MVP
- **Date / phase:** 2026-08-27 / Phase 0
- **Requirement ID(s):** ARCH (self-critique §21b), SCOPE-2.1, SCOPE-2.2
- **Ambiguous or undecided:** Patient-record field units may differ from guideline-criteria units (e.g. mg/dL vs mmol/L); the brief does not address unit conversion.
- **Decision & rationale:** The MVP assumes a single-locale English corpus and does **not** perform unit conversion. A unit mismatch between a record field and a criterion surfaces as `missing_critical_info` / `phi_ambiguity` (i.e. "cannot confirm") rather than a silent conversion. Silent conversion is a known error source and is out of scope.
- **Reversible?:** yes — a normalization layer can be added; until then the fail-safe behaviour holds.

### 26. Default dev guideline corpus is operator-provided real PDFs, not generated synthetic docs
- **Date / phase:** 2026-09-01 / Phase 1 (Checkpoint 1)
- **Requirement ID(s):** PRD-006, PRD-001, PRD-A2 (supersedes / narrows DEVIATIONS #22)
- **Ambiguous or undecided:** DEVIATIONS #22 made `fetch_sample_guidelines.py` *generate* three tiny synthetic Markdown "guidelines" by default. Those do not resemble how real clinical guidelines are structured (multi-page, GRADE recommendation sets, clinical pathways, dosing tables, algorithm figures), so ingestion/chunking/retrieval/citation work built on them would be tuned to an unrepresentative fixture.
- **Decision & rationale (PROPOSED):** `data/sample_guidelines/` holds **only the real corpus**. The script (renamed `prepare_sample_guidelines.py`, `make prepare-guidelines`; `fetch-guidelines` kept as an alias) no longer generates content by default: it scans for real guideline files, checks each has a `manifest.json` entry, and warns (does not invent) for any missing metadata. Generating the tiny synthetic set is now opt-in (`--allow-synthetic` / `GUIDELINES_ALLOW_SYNTHETIC=true`) and is a **CI-only offline fixture**; those files move to `backend/tests/fixtures/guidelines/`. With no real docs and no flag the script exits non-zero telling the operator to add guideline PDFs.
- **Reversible?:** yes — the synthetic generator remains available behind a flag; nothing about the data model changes.

### 27. Guideline document-format heterogeneity — chunking needs format profiles, not one recommendation model
- **Date / phase:** 2026-09-01 / Phase 1 (Checkpoint 1)
- **Requirement ID(s):** ARCH-013 (§6), SCOPE-1.2 (§9.1), PRD-004
- **Ambiguous or undecided:** ARCHITECTURE.md §6 rule 1 and its Rationale assume every guideline is a set of numbered GRADE recommendation statements ("… is recommended. (Strong recommendation, moderate certainty)"). The provided corpus shows at least three distinct formats: **GRADE recommendation set** (WHO 2017/2024), **clinical protocol / care pathway** (Kenya MOH: numbered pathways, step lists, dosing tables, algorithm flowcharts — no GRADE statements), and **narrative/background**. "Atomic recommendation" is therefore publisher/format-dependent.
- **Decision & rationale (PROPOSED):** Introduce a per-document `format_profile ∈ {grade_recommendations, clinical_protocol, narrative}` (detected at ingest and/or set in the manifest). Each profile defines the atomic unit: `grade_recommendations` → recommendation statement + strength/certainty/population qualifiers (current rule 1); `clinical_protocol` → a numbered protocol step / pathway node + its sub-bullets + any dose/parameter table bound to that step, kept atomic (`chunk_type = protocol_step`); `narrative` → prose chunking only (rule 2). SCOPE-1.2 reported-content framing gains a protocol variant ("Protocol X, step N states…", "Per [source] pathway, the documented step is…") — still reported-content, never directive. §6 Rationale reworded to say the atomic unit is profile-dependent while keeping the safety argument.
- **Reversible?:** yes — additive: a new `chunk_type` value and a per-document enum; documents without a detected profile fall back to `narrative`.

### 28. Figures / algorithms / flowcharts — add a `figure` chunk type; OCR out of scope
- **Date / phase:** 2026-09-01 / Phase 1 (Checkpoint 1)
- **Requirement ID(s):** ARCH-013 (§6), ARCH-015 (§8.3), ARCH self-critique §21a
- **Ambiguous or undecided:** §6 covered prose / recommendation / table / list / criteria but was silent on figures. The Kenya MOH protocol is algorithm/flowchart-heavy and a clinical-pathway flowchart is frequently the content a clinician needs; a citation landing "near" a figure with no figure handling would have wrong or empty support.
- **Decision & rationale (PROPOSED):** Add `chunk_type = figure`: one chunk per figure holding the caption, any text extractable from the image region as **vector text already in the PDF** (embedded text layer), the nearest heading, and a stored page + bounding-box reference so the citation view can show the figure crop. **OCR is out of scope for MVP** — a figure with no extractable text is retained for citation/`expand_context` but is embedded from its caption only, weighted down in dense retrieval, and flagged so the §8.3 grounding check treats a caption-only / no-text figure as **at most `weak` support** (never the sole support for a claim → forces `weak_support` queue or escalation). Low overall extractable-text ratio → low `parse_quality`, visible badge, admin review before the document's chunks become retrievable.
- **Reversible?:** yes — additive `chunk_type` value + one grounding rule.

### 29. Document ingest metadata is operator-supplied via a per-file manifest, never inferred from PDF metadata — new ARCH-038; add `document.licence`
- **Date / phase:** 2026-09-01 / Phase 1 (Checkpoint 1)
- **Requirement ID(s):** ARCH-038 (NEW — proposed), ARCH §5.1, ARCH §4.1, PRD-004, PRD-A2
- **Ambiguous or undecided:** §5.1 step 1 says `publisher` / `version_label` / `effective_date` are "recorded" but never says from where. All three provided PDFs have **empty PDF metadata** (`/Title` is null); version/effective-date live in the filename / cover page only. There is also no place to record each document's licence, which PRD-A2 requires be checked.
- **Decision & rationale (PROPOSED):** New decision **ARCH-038** — `POST /ingest/documents` takes the file plus a metadata object (`title`, `publisher`, `external_ref`, `version_label`, `effective_date`, `licence`, `topic_tags`, optional `format_profile`, optional `language`); batch/bundled ingestion reads the same fields per file from a sidecar `data/sample_guidelines/manifest.json`. Metadata is **never auto-committed from PDF metadata**; a cover-page heuristic may only *suggest* values for the admin to confirm. Add a `licence` column to `corpus.document`. Repo ships `data/sample_guidelines/manifest.example.json` (tracked) and gitignores the real `manifest.json` (same pattern as `.env`).

### 48. BM25 sparse vectors: stable-hash indices + Qdrant server-side IDF, not a fitted corpus vocabulary
- **Date / phase:** 2026-09-14 / Phase 2
- **Requirement ID(s):** ARCH §6 ("Sparse / BM25"), ARCH-002, ARCH-003
- **Ambiguous or undecided:** ARCH §6 asks for "a standard BM25 term weighting over a clinical-aware analyzer," stored as a Qdrant named sparse vector. The first implementation of `app/retrieval/sparse.py` (same day, superseded before anything else was built on it) fit `rank_bm25.BM25Okapi` per ingestion batch and built a batch-local `term -> index` vocabulary. Re-examining that design before wiring it into `app.retrieval.hybrid`: a Qdrant collection is shared across every ingested `document_version`, so two independently-fitted local vocabularies (e.g. from two separate ingestion batches) would silently assign the SAME term to DIFFERENT indices in different chunks — corrupting sparse dot-product scores across documents the moment more than one batch shares a collection. - **Decision & rationale:** Replaced the fitted-vocabulary design with a stable hash (`blake2b`, 64-bit truncated, mod 2^24) mapping each analyzed term to a fixed index, computable independently at ingest time and query time with no shared state to persist or keep in sync. Each chunk's sparse vector stores raw term frequency (`Counter` over `analyze(text)`); Qdrant's `SparseVectorParams(modifier=Modifier.IDF)` (set in `QdrantVectorStore.ensure_collection`) multiplies by the corpus's own IDF at query time, computed server-side from what is actually indexed — Qdrant's documented pattern for BM25-like sparse search, verified against a real (embedded, in-memory) Qdrant instance in this session (`tests/test_vectorstore.py`, plus an ad hoc check confirming the IDF modifier measurably changes ranking). This is TF × server-computed-IDF, not the full saturating BM25 formula (no per-document length normalisation / k1 term) — "BM25-style," a narrower claim than the textbook formula, but correct-by-construction across a multi-batch shared collection, which the fitted-vocabulary design was not.
- **Reversible?:** yes — `app/retrieval/sparse.py` has no persisted state; the analyzer function (`analyze`) is unchanged from the superseded design, only the indexing scheme changed, before any chunk had actually been upserted with the old scheme.

### 56. Real Postgres round-trip found and fixed a timezone-drop bug across the whole schema
- **Date / phase:** 2026-09-14 / Phase 2

### 63. Row-level security: fail-open when `app.current_patient_scope` is unset; audit append-only trigger as defense in depth
- **Date / phase:** 2026-09-14 / Phase 2
- **Requirement ID(s):** ARCH-034, ARCH-035, ARCH §4.2/§4.3, PRD-NG-011 (one patient per session)
- **Ambiguous or undecided:** the Phase-1 placeholder migration's docstring requires RLS on `records.*` and `memory.patient_context` "keyed on the `app.current_patient_scope` GUC" and an audit-schema trigger rejecting UPDATE/DELETE, but specified neither the policy's exact logic nor which `records.*` tables actually need it.
- **Decision & rationale:**
  - **Scope:** RLS enabled on `records.patient` (key: `id`), `records.patient_record` (key: `patient_id`), and `memory.patient_context` (key: `patient_id`) — the tables that actually hold per-patient rows. **Not** `records.record_field_policy`: it's global (role, purpose, field_path) → effect configuration with no `patient_id` column at all — enabling RLS there would be a category error, not extra safety.
  - **Policy logic — fail-open when the GUC is unset or empty**: `USING (current_setting('app.current_patient_scope', true) IS NULL OR ... = '' OR <key>::text = current_setting(...))`. This was the pivotal judgment call: every patient-data-touching path built so far (`ingest_records`, `_run_process_document`'s persistence, the real-Postgres verification in DEVIATIONS #57) uses `app.db.session.session_scope()` with **no** `patient_scope` argument, which never sets the GUC at all — a fail-closed policy (deny when unset) would have silently broken every one of those already-verified, already-working flows the moment this migration was applied. Fail-open matches the actual, intended access pattern: service/ingestion/admin operations (no GUC) see everything; a future per-conversation query path (Phase 3/4, `session_scope(patient_scope=<id>)`, one patient per session per PRD-NG-011) gets narrowed to exactly that patient. `app.api.deps.get_db` does not yet set `patient_scope` from the caller's principal either way — that wiring is still Phase 4, per its own docstring.
  - **RLS applies to `hrag_app`, not to Alembic**: Postgres exempts the table owner (and superusers) from RLS by default. Since the elevated `hrag_admin` role (DEVIATIONS #61) owns these tables, RLS constrains only the restricted runtime role — exactly the intended blast radius.
  - **Audit trigger, not just the role GRANT**: a `BEFORE UPDATE OR DELETE` trigger function on `audit.audit_event` that unconditionally `RAISE EXCEPTION`s. Unlike RLS, Postgres triggers are **not** bypassed for the table owner — verified directly: connected as `hrag_admin` (the owner/superuser) and confirmed both `UPDATE` and `DELETE` are rejected by the trigger, even though that role's role-level GRANTs alone would have permitted them. This is the actual "defense in depth beyond the role GRANTs" the placeholder migration's docstring asked for, not a restatement of the existing REVOKE.
  - **Verified, not assumed**: full round trip against a real (ephemeral, Dockerized) Postgres — `alembic upgrade head` as `hrag_admin`; connected as `hrag_app` and confirmed (a) no GUC set → all rows visible, (b) GUC set to one patient's id → only that patient's row visible, (c) GUC set to `''` → fail-open, all rows visible again; `alembic downgrade` back to the Phase-1 placeholder cleanly drops the policies/trigger/tables, then `alembic upgrade head` re-applies cleanly. `ingest_records` re-verified end-to-end connected as `hrag_app` against the fully-migrated, RLS-enabled schema.
- **Reversible?:** yes — `downgrade()` drops the trigger, function, and all three policies (and disables RLS) before dropping any table; verified by actually running it.

### 66. Auto-question generator: rejected an operator-supplied prompt design that asked for patient-specific management questions; deterministic word-overlap validator; scope-1 enforced twice
- **Date / phase:** 2026-09-14 / Phase 2
- **Requirement ID(s):** ARCH §15.1 steps 3–6, PRD-060, PRD-061, PRD-064, CDS-FUTURE.md / SCOPE-2.3 (the hard boundary), CLAUDE.md §3 rule 4
- **Ambiguous or undecided:** the operator supplied a "SIMULATED CLINICAL QUESTION GENERATION PROMPT" as a starting point and asked for improvements before implementation. Read closely against CLAUDE.md §3 rule 4 ("the CDS boundary is hard... stop and flag rather than implementing a workaround") rather than adopted as-is.
- **Decision & rationale:**
  - **The scope problem, flagged before writing code:** the supplied prompt's task instruction asks for a question "focused on either diagnosis of SBI, or **management of suspected or confirmed SBI**" for "this patient," inviting "the type of question a clinician might ask during... clinical decision-making." That is a materially different target than ARCH §15.1 step 4's mandated template — *"What does the guideline recommend for a patient presenting with {presentation}?"*, explicitly never "what should happen next for this patient." A model given "ask a management question about this specific infant" will readily produce something like "Should this infant be started on empiric IV antibiotics given the grunting and hypothermia?" — a SCOPE-2.3 next-step-recommendation question, not a SCOPE-1 guideline lookup. Because this generator's output becomes the actual query set the RAG system is evaluated against, adopting the prompt as given would mean the eval harness itself starts manufacturing scope-violating queries — the opposite of what PRD-061/ARCH §15.1's "scope-1 framing only" rule exists to prevent. Flagged this to the operator directly rather than silently adjusting or silently adopting; the operator's follow-up asked for the corrected version to be built.
  - **What was kept from the supplied prompt** (genuinely useful, adopted): structured field-category extraction (`_field_subset_lines` — demographics, admission vitals, anthropometrics, signs/symptoms, matching what the record schema actually has, since our `PatientRecord` has no maternal-history section — a category from the supplied prompt that was dropped rather than fabricated fields to fill it), the "use only information available at admission" discipline (already free for single-snapshot synthetic records, but stated explicitly in the system prompt as a rule the model must follow, not just an accident of our data), and "never state an undocumented finding as absent" (`_field_subset_lines` omits absent fields entirely rather than writing "no history of X").
  - **What was replaced:** the question-focus instruction now mandates ARCH §15.1 step 4's exact template shape and explicitly lists banned phrasings ("should," "what treatment," "next step," "what medication/dose"). Enforced **twice**, not just in the prompt: `_is_scope1_framed` re-checks the model's actual output after generation (reusing `app.grounding.wording.has_directive_phrasing` for the "you should"/"administer X to this patient" patterns, plus a question-specific pattern set) and rejects+retries on a miss, exactly like the grounding-failure retry path — a model can drift from instructions, so the check that matters is on the output, not just the instruction.
  - **Validator approach:** `validate_narrative` is deterministic word-overlap against the record's own field *values* (never field names — this intentionally reads plaintext values, unlike `field_index`'s no-values rule, because the narrative is about to be shown to a clinician regardless), not a medical NER/entity-linking model — none is in scope, and "determinism where it matters" (CLAUDE.md §4) favours a checkable rule. A fixed, small, literal allowlist covers question-shape scaffolding words ("what," "does," "guideline," "recommend," ...) and units-of-measurement ("weeks," "grams," "bpm," ...) — the latter added after a real test failure showed "34 weeks gestation" being flagged as fabrication when only the bare number "34" was in the vocabulary; deliberately did **not** add clinical-finding words ("breathing," "heart," "oxygen") to that allowlist, so a genuinely fabricated finding stays catchable. Logged as an approximation, not a true entity linker: a paraphrase using none of the record's words can slip past undetected in the other direction (a false negative on fabrication) — an acknowledged limitation, not silently assumed exact.
  - **Test-only fake gateway, not the production stub:** `LLMGateway.chat()`'s offline `stub_chat` deliberately never generates real content (already established when `LLMGateway.chat()` was implemented, DEVIATIONS #54's discussion) — a dedicated `_FakeGateway` test double (returning canned, test-controlled narrative text) is what makes `generate_question` testable offline, per the resolution agreed at that time.
- **Reversible?:** yes — the prompt template, the violation-pattern list, and the validator's allowlists are all isolated, swappable constants with their own tests; none of this is committed to the DB schema or any other module's contract.

- **Ambiguous or undecided:** ARCH §4.2/§17.3 specify `record_field_policy(role, purpose, field_path) -> allow|deny|mask` as the field-level gate but not (a) what happens when no policy row matches a given `(role, purpose, field_path)`, (b) whether a policy can be granted at coarser-than-per-field grain, or (c) what `mask` actually returns to the caller.
- **Decision & rationale:**
  - **Fail-closed default.** `app/auth/rbac.py::resolve_field_effects` returns `deny` when no policy row matches at all — a field is never readable unless some row explicitly permits it, consistent with this phase's broader shift away from permissive defaults (`current_principal`, DEVIATIONS #86).
  - **Wildcard field_path.** A `(role, purpose, "*")` row is a fallback applied to every field path without its own exact-match row, checked only after the exact match misses. This makes seeding tractable (one row can grant "everything this role/purpose needs" instead of one row per field) while still letting an operator carve out per-field exceptions with a more specific row. Not specified in ARCH; a deliberate seeding-ergonomics choice, not required by any requirement ID.
  - **Bulk resolution.** `resolve_field_effects` (plural) fetches every `(field_path, effect)` row for a `(role, purpose)` in one query and resolves the whole requested batch in Python, rather than the single-field `resolve_field_effect` being called once per field (which would be N/2N round trips for an N-field `get_patient_fields` call). `resolve_field_effect` (singular) remains as a convenience wrapper.
  - **`mask` semantics.** `get_patient_fields` substitutes a fixed placeholder string (`app.records.access._MASKED_PLACEHOLDER`, `"[masked by policy]"`) for a `mask`-effect field's real value — present in the result (so the caller can tell "restricted" apart from "not on file", unlike `deny` which omits the key entirely) but never the plaintext. ARCH doesn't specify the placeholder shape; chosen to be unambiguous and never collide with a real clinical value.
  - **`get_patient_fields` now requires `actor_role`** (previously optional, audit-log-only) since it is the input to the policy gate. Every requested field that actually exists in the decrypted record is resolved through the policy table; `_NEVER_RETURNED_FIELDS` (identity fields) and the caller's own requested-field list remain a hard floor beneath the policy table, not overridable by any policy row (DEVIATIONS #70). The audit event's `detail` now also records `denied_fields`/`masked_fields` (only when non-empty) alongside the existing full `record_fields` (requested) list.
  - **`patient_record_agent.py`'s role selection.** `actor_role` was previously `state["roles"][0]` — harmless while `actor_role` was audit-log-only, but `Principal.roles` is a `frozenset`, so `[0]` is a per-process-hash-dependent, not meaningful, choice. Now that `actor_role` is access-determining, that ambiguity became a real bug risk (a dual-role principal could nondeterministically get gated as the wrong role). Fixed via `_select_actor_role`: prefer `"clinician"` when the principal holds it (this agent's own purpose is clinical-care field access, and `/query` already requires the `clinician` route permission), else the lexicographically-first role — deterministic either way. `retrieval_agent.py`/`escalation_agent.py` keep the old `roles[0]` pattern unchanged; their `actor_role` remains audit-label-only, not access-determining, so the same fix isn't needed there (flagged here in case a future change makes it access-determining too).
  - **No uniqueness constraint added on `(role, purpose, field_path)`.** The table has no unique/composite-key constraint (Alembic migration `ba3c23a19ce9`); a duplicate-key operator seeding mistake is possible. Not fixed now (would need a new migration + real-Postgres re-verification, out of scope for this change) — `resolve_field_effects`' query returns one `effect` per `field_path` via a plain `dict(...)` over the result rows, so a duplicate silently keeps whichever row the DB happens to return last, rather than crashing. Flagged for the seeding task (`scripts/seed_db.py` record_field_policy rows, still pending in Phase 4) to seed carefully / add the constraint then.
  - Verified against a real ephemeral Postgres (migrated to `ba3c23a19ce9`): exact-match-over-wildcard precedence, fail-closed default with zero policy rows, `mask` substitution, and `get_patient_fields` end-to-end (encrypt → policy-gate → decrypt-and-project) all confirmed with real seeded `record_field_policy` rows and a real encrypted `patient_record` row, not just offline mocks.
- **Reversible?:** yes — additive to the existing `record_field_policy` table (no schema change); `get_patient_fields`'s new required `actor_role` param is the only signature change, and its one production caller (`patient_record_agent.py`) already passed it by keyword.

  - **No `asyncio.to_thread`/blocking-in-the-event-loop complexity.** A "hybrid" design (enqueue, then block-with-timeout inside the sync route before falling back to a job handle) was considered and rejected: it would need `asyncio.to_thread` to avoid blocking the whole event loop on `AsyncResult.get()`, adding real complexity to the hot path for a benefit (occasionally saving one client a second poll) that doesn't justify it. Plain enqueue-and-return is simpler and the additive route is what actually gets exercised only when a caller opts in.
  - **Shared logic, not two copies.** Split `app.api.routes.query`'s persistence/audit/response-assembly logic out into `app.agents.query_pipeline` (`prepare_query`, `assemble_and_persist_response`) and the lazy-singleton graph invocation into `app.agents.graph_runtime` (`invoke_graph`) — both the synchronous route and the new `app.agents.tasks.run_query` Celery task call the exact same functions, so "what a completed query run persists/audits" is defined once. `prepare_query` (conversation resolution, the user's turn, the `query` audit event) runs **synchronously** even on the async path — the attempt should be recorded immediately, not only once/if the Celery run completes; only the graph invocation + response persistence move to the worker.
  - **Not idempotency-safe on task retry** — flagged explicitly in `app.agents.tasks`'s own module docstring rather than solved here: `task_acks_late`/`task_reject_on_worker_lost` (`app.worker`, unchanged) mean a worker crash mid-task re-queues it, and no idempotency key exists to stop a retry from double-writing the assistant turn/audit row. This is the same property `process_document` already has (ARCH §21c self-critique item 5 already names this class of problem); not newly introduced, not newly solved.
  - Verified end-to-end against real infrastructure, not just offline mocks: a real Redis broker (task registration confirmed in `celery_app.tasks`, a real `send_task` enqueue confirmed landing in the broker's queue) and a **real, separate Celery worker OS process** consuming from it, persisting to a real ephemeral Postgres — a dispatched task with a real `conversation_id` came back `SUCCESS` with the expected `QueryResponse` shape, and the `answer` audit event + assistant `message` row were confirmed written by the worker process via direct SQL. (The worker's own graph invocation was stubbed in this verification run only — same reasoning as other agent-layer real-Postgres passes this phase: the graph's own correctness is already covered by `test_agent_graph.py` and doesn't need re-proving through Celery specifically; what needed proving here was the dispatch/consume/persist/result-backend plumbing, which is now confirmed real.)
- **Reversible?:** yes — `POST /query/async`/`GET /query/jobs/{job_id}` and `app.agents.tasks.run_query` are wholly additive; the `query_pipeline`/`graph_runtime` extraction is a pure refactor (the synchronous route's behavior and its existing test suite are unchanged, confirmed by running the full suite before and after).

### 95. End-to-end `docker compose up` verification pass — six real bugs found and fixed, none of which any offline test or single-script real-Postgres check could have caught
- **Date / phase:** 2026-09-14 / Phase 4
- **Requirement ID(s):** ARCH-036, PRD-106
- **Ambiguous or undecided:** none — this was a verification pass (prompt.txt's Phase 4 checklist), not a design decision. Everything below is a genuine bug, found by actually running the full stack (proxy, api, worker, postgres, redis, qdrant, llm-gateway, frontend under the `dev` profile) and driving real HTTP requests through it end to end, rather than by inspecting the compose file or re-running isolated real-Postgres scripts (the discipline used throughout this phase, which — as this pass shows — cannot catch bugs that only manifest when multiple real services and multiple concurrently-open DB sessions interact).
- **What was verified, and what broke:**
  1. **`deploy/nginx/nginx.conf`'s `/api/` proxy silently 404'd every request.** `proxy_pass http://api:8000/;` (trailing slash) strips the `/api/` prefix nginx matched on — but the FastAPI app mounts every route under `/api` (`app.main`'s `api_base_path`), so the backend never had a route at the stripped path. Every request through the proxy 404'd despite the identical path working when called directly against the `api` container. Fixed: `proxy_pass http://api:8000;` (no trailing slash) — nginx then forwards the original URI, `/api/...`, unchanged.
  2. **`POST /ingest/documents` uploads were invisible to `worker`.** Neither `api` nor `worker` mounted a volume for `SAMPLE_GUIDELINES_DIR`/`PATIENT_RECORDS_DIR` — an uploaded file landed only on `api`'s own ephemeral container filesystem, so `worker`'s `process_document` task (a *different container*) got `FileNotFoundError` trying to parse it. Fixed: added `./data/sample_guidelines` and `./data/patient_records` as bind mounts shared by both `api` and `worker` in `docker-compose.yml` — also makes uploads survive a container recreate, and matches the ingest route's own docstring ("the same directory an operator manually drops PDFs into").
  3. **The same bind mount then hit a host/container UID mismatch.** `api`/`worker` run as `user: "10001:10001"` (Dockerfile's documented non-root rationale); the host `data/sample_guidelines`/`data/patient_records` directories were `1000:1000`, mode `775` — group-writable only for gid 1000, so uid 10001 could read but not write, and the upload failed with `PermissionError`. Fixed pragmatically (dev-only, non-secret data): `chmod -R a+rwX` on both directories. A real fix that survives a fresh clone needs either a documented one-time host-prep step or an entrypoint-level chown; not fully resolved — flagged rather than left silently working only because this session happened to fix the permissions by hand.
  4. **The LangGraph Postgres checkpointer's lazy setup self-deadlocked on the very first real `/query` request.** `PostgresSaver.setup()` (triggered lazily, on first graph invocation, per `app.agents.graph_runtime`'s original design) runs `CREATE INDEX CONCURRENTLY`, which — per Postgres's own documented semantics — waits for *every* other transaction open anywhere in the database to finish, not just ones touching the same table. The first real request's own `get_db()` session had an uncommitted `query` audit-event INSERT sitting open (the whole request was one long transaction) at the exact moment the lazy checkpointer setup ran on a separate connection — so the `CREATE INDEX CONCURRENTLY` waited on a transaction that could not close until the very request doing the waiting finished. A real HTTP request through nginx sat until the proxy's own `proxy_read_timeout` (120s) gave up with a 504; the request was, in fact, still blocked server-side afterward (confirmed: a direct request to the `api` container's own `/healthz`, bypassing nginx, also timed out — the single uvicorn process had nothing else free to serve). Fixed: warm the checkpointer once, eagerly, in `app.main`'s FastAPI `lifespan` startup hook (`app.memory.checkpointer.get_checkpointer()`/`close_checkpointer()`) — before any request can possibly hold an open transaction. Confirmed safe for the offline suite: `TestClient(fastapi_app)` used without `with` (every existing test in this codebase) does not trigger FastAPI/Starlette lifespan events, so this doesn't touch any of the 465 offline tests (verified by running the full suite before and after).
  5. **The audit hash-chain has a real concurrency race**, found immediately after fixing #4 let real requests actually complete: `GET /admin/audit?verify=true` reported a broken link. Root cause: `write_event`'s `_fetch_last_row_hash` (`app/audit/log.py`) does a plain `SELECT ... ORDER BY id DESC LIMIT 1` with no serialization; two `write_event` calls on **different sessions** (`POST /query`'s own `get_db()` session writing `query`, and `app.retrieval.hybrid.retrieve` — called from inside the graph run, on its own separate session, per `app.agents.retrieval_agent`'s design — writing `retrieval` moments later and committing independently) can both read the same "last row" before either INSERT is visible to the other, producing two rows that share one `prev_hash`. Reproduced directly (not just inferred from the proxy-request symptom): 8 threads, each its own real session, racing `write_event` against the real Postgres this stack was already running — reliably broke the chain. **First fix attempt — `SELECT ... FOR UPDATE` on the last row — was tried and confirmed NOT to work**, by the same repro: locking an *existing* row only blocks a second transaction from locking that *same* row; a fresh INSERT never modifies it, so once the lock holder commits, everyone blocked on it wakes and proceeds with the now-stale row they'd already planned to use. **Actual fix:** `pg_advisory_xact_lock` (a fixed key, `app.audit.log._CHAIN_LOCK_KEY`) taken before the read — a transaction-scoped advisory lock that serializes the whole read-last-hash-then-insert sequence itself, for every caller, regardless of which specific row anyone reads; auto-releases at COMMIT/ROLLBACK. Re-ran the same 8-concurrent-writer repro against the fix: zero new breaks (the table's pre-existing broken rows from before the fix remain broken forever, correctly — audit is append-only, historical corruption can't be un-recorded, only prevented going forward).
  6. **The fix for #5 then reintroduced a variant of #4's deadlock.** `POST /query`'s route session (`get_db()`) still stayed open for the whole request, including the entire graph invocation; the advisory lock from #5 is held for the writing transaction's *full* lifetime — so the `query` event's lock, held by the still-open outer request transaction, now blocked `retrieval`'s own `write_event` call (a different, separate session) for the *whole rest of the request*, which could not finish (and release the lock) until `retrieval` — the thing it was blocking — returned. Same proxy-timeout symptom as #4, confirmed via `pg_stat_activity`: one session `idle in transaction` holding the uncommitted `query` INSERT, another `active` blocked on `Lock:advisory`. **Root architectural fix, not a narrower patch:** `POST /query`/`POST /query/async` no longer use `Depends(get_db)` at all — a single session that outlives a multi-session computation in the middle of a request is the actual anti-pattern, and it would have kept causing new variants of this same class of bug for any future code that both (a) writes audit rows early in a request and (b) later calls something that opens its own separate session and also writes an audit row, no matter how the specific lock/serialization mechanism worked. Now uses two short-lived, explicit `_SESSION_SCOPE()` calls (a new module-level test seam matching every agent module's existing `_SESSION_SCOPE` convention) — one for `prepare_query` (commits and closes *before* the graph runs), one for `assemble_and_persist_response` (opened only *after* the graph returns) — so no transaction this route holds ever overlaps the graph invocation, eliminating the whole class of hazard rather than the one manifestation. Verified: 5 real concurrent `/query` requests through the full stack, all fast (20-55ms) and correct; `GET /admin/audit?verify=true` afterward showed zero new breaks.
  - **Also fixed while verifying:** `.env.example`'s `DEVJWT_SIGNING_KEY` was still the pre-Phase-4 19-byte placeholder (`dev-only-change-me`), inconsistent with `app/config.py`'s own default already lengthened to 38 bytes this phase (DEVIATIONS #86) — a real deployment following `.env.example` would still have hit PyJWT's `InsecureKeyLengthWarning` on every login. Updated `.env.example` to match; confirmed the warning disappears with a real login through the running stack.
  - **What was confirmed working, unmodified:** TLS termination + HTTP→HTTPS redirect (self-signed dev cert per `deploy/tls/README.md`); `alembic upgrade head` and `scripts/seed_db.py` (including this phase's new migration `e6bd710e1911` and `record_field_policy` seed rows) run cleanly via `docker compose exec api`; `POST /auth/dev-login` end to end; full document ingestion (`POST /ingest/documents` → `process_document` on `worker` → real Qdrant collection/points) once #2/#3 were fixed; `POST /query` and `POST /query/async`/`GET /query/jobs/{id}` producing correct, well-formed responses (disclaimer always present) against a real ingested corpus; `GET /admin/audit` with real accumulated events across `login`/`query`/`retrieval`/`answer`/`ingestion` actions and working hash-chain verification.
- **Reversible?:** yes throughout — nginx config line, two new bind-mount volume entries, a `chmod`, a startup-hook reordering, a locking-primitive swap, and a session-scoping change in one route module; none is a schema or external-contract change. All six are also each independently the *kind* of finding that would keep recurring for any future request-handling code with a similar shape (a session held open across a multi-session sub-computation) — flagged accordingly in the code comments at each fix site, not just here.
